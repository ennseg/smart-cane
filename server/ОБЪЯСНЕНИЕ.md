## 1. Общая архитектура

Рис. 4 документа архитектуры делит сервер на четыре блока. В коде они устроены так:

| Блок на рис. 4 | Где в коде | Что делает |
|---|---|---|
| **Device API (FastAPI)** | `cane_server/api/` | Приём `POST /api/v1/telemetry` (и синонима `/event`), проверка токена, HMAC и JSON-схемы, ответ `ack + cmd + cfg` |
| **Rules / Alert Service** | `cane_server/services/` | Правила тревог (таблица 7), антифлуд, «устройство молчит», расчёт «N мин назад», очередь команд |
| **Bot Handlers (aiogram 3)** | `cane_server/bot/` | Команды таблицы 8, белый список chat_id, кнопки |
| **База данных** | `cane_server/storage/` | Таблицы devices, guardians, positions, events, очередь команд и др. |

Всё работает в **одном процессе Python и одном потоке** с асинхронным циклом событий (event loop).
В нём одновременно крутятся:

```
                       ┌──────────────────── один процесс python -m cane_server ────────────────────┐
 ESP32 ──HTTP POST──►  │ uvicorn → FastAPI → device_routes → TelemetryIngestor ─┐                   │
                       │                                                        ├─► SQLite (WAL)    │
 Telegram ◄─polling──  │ aiogram Dispatcher → handlers (/where, /status, ...) ──┤                   │
                       │                                                        │                   │
                       │ OutboxDispatcher.run_forever()  ◄── таблица outbox ────┘                   │
                       │        │ sendMessage / sendLocation / editMessageLiveLocation              │
                       │        ▼                                                                   │
 Telegram Bot API ◄────│ aiogram Bot (HTTP-клиент; в DRY_RUN — RecordingSession, пишет в лог)       │
                       │                                                                            │
                       │ BackgroundMonitor.run_forever(): молчание, напоминания SOS, TTL /where     │
                       └────────────────────────────────────────────────────────────────────────────┘
```

Главная идея: **приём данных и отправка в Telegram развязаны через таблицу `outbox`**. Обработчик
запроса устройства не ходит в Telegram. Он в одной транзакции сохраняет пакет и записывает в outbox,
какие сообщения нужно отправить. Отдельная фоновая задача их отправляет, а при ошибках повторяет.
Это шаблон **transactional outbox**, разобранный в п. 6.5 и 10.

## 2. Путь данных: от устройства до сообщения в Telegram

Как SOS доходит до сопровождающего (подробно — в п. 7.1):

1. ESP32 отправляет `POST /api/v1/telemetry` с JSON, заголовками `X-Device-Token` и `X-Signature`.
2. **uvicorn** (HTTP-сервер, как встроенный Tomcat/Netty) передаёт запрос в **FastAPI**,
   а тот вызывает функцию `receive_packet` из `api/device_routes.py`.
3. `read_limited_body` читает сырые байты тела (не больше 4 КБ). Подпись считается **по байтам**,
   поэтому тело нельзя сразу разбирать в объект.
4. Открывается транзакция `ctx.db.transaction()` (аналог `@Transactional`).
5. `authenticate_device` ищет устройство по SHA-256 токена, сравнивает хеши в постоянное время,
   затем проверяет HMAC.
6. `decode_json` и `validate_packet` превращают байты в pydantic-модель `TelemetryPacket` (аналог DTO
   с Bean Validation) и сверяют `dev` с устройством.
7. `TelemetryIngestor.handle` по шагам:
   - `PresenceService.register_contact` отмечает контакт; если устройство числилось «молчащим»,
     пишет «связь восстановлена»;
   - `accept` проверяет дубликат `seq`, сохраняет пакет и позицию, обновляет снимок состояния
     устройства, передаёт пакет в `CommandService.on_packet` (ответ на `/where`) и
     `AlertService.on_packet` (тревоги);
   - `AlertService` создаёт строку в `events`, проверяет антифлуд, формирует текст и через `Notifier`
     кладёт в `outbox` по две строки (текст и карта) на каждого привязанного сопровождающего;
   - `finish_exchange` берёт из очереди команду для устройства (`locate_now`), если она есть.
8. Транзакция фиксируется (commit), устройству уходит `{"ack": seq, "dup": false, "cmd": ..., "cfg": {...}}`.
9. `ctx.outbox.wake()` будит фоновую задачу доставки, не дожидаясь её таймера.
10. `OutboxDispatcher.deliver_due` читает строки outbox и вызывает `bot.send_message` и `bot.send_location`.
    Они уходят в Telegram Bot API, а в режиме DRY_RUN — в `RecordingSession`, которая пишет их в лог.
11. Telegram доставляет push-уведомление на телефон сопровождающего.

## 3. Словарь «Python ↔ Spring Boot»

| Здесь | Аналог в Spring | Комментарий |
|---|---|---|
| FastAPI + `APIRouter` | Spring MVC / WebFlux, `@RestController` | Роут — функция с декоратором `@router.post(...)` |
| uvicorn | встроенный Tomcat / Netty | Сервер ASGI (асинхронный аналог Servlet API) |
| pydantic `BaseModel` с `Field(ge=..., le=...)` | DTO + Jackson + Bean Validation (`@Min`, `@Max`, `@Pattern`) | `model_validate` одновременно разбирает и проверяет |
| `@model_validator` | класс-уровневый `@Constraint` | Правило «при `fix=true` обязательны `lat`/`lon`» |
| pydantic-settings `Settings` | `@ConfigurationProperties` + `application.properties` | Поля читаются из окружения и `.env` |
| SQLAlchemy 2.0 ORM (`Mapped[...]`) | JPA/Hibernate (`@Entity`, `@Column`) | `mapped_column(unique=True)` и т. п. |
| `AsyncSession` | `EntityManager` / persistence context | Изменения объектов отслеживаются и сохраняются при commit (dirty checking) |
| `storage/repositories.py` | Spring Data репозитории | Функции-запросы. Писать SQL руками не нужно |
| `Database.transaction()` | `@Transactional` | Явный контекстный менеджер `async with` вместо аннотации |
| `session.flush()` | `entityManager.flush()` | Отправить INSERT сейчас, чтобы получить `id` |
| `AppContext` + `build_context()` | `ApplicationContext` + `@Configuration`/`@Bean` | Ручное внедрение зависимостей через конструкторы |
| `lifespan` в FastAPI | `SmartLifecycle`, `@PostConstruct`/`@PreDestroy` | Код до `yield` выполняется при старте, после — при остановке |
| `asyncio.create_task(...run_forever())` | `@Scheduled` / `TaskScheduler` | Фоновые задачи в том же процессе |
| `app.add_exception_handler(ApiError, ...)` | `@ControllerAdvice` + `@ExceptionHandler` | Единый формат ошибок `{"error","detail"}` |
| aiogram `Router` + `register(handler, Command("where"))` | `@Controller` + маппинг команд | Хендлер — функция, aiogram сам подставляет аргументы по имени |
| aiogram `BaseMiddleware` | `HandlerInterceptor` / Spring Security фильтр | Белый список chat_id |
| `RecordingSession` (DRY_RUN) | `MockRestServiceServer` / WireMock | Подмена HTTP-слоя клиента Telegram |
| pytest fixture | JUnit `@BeforeEach` + `@MockBean` + Spring TestContext | Фикстуры собирают окружение теста |
| `httpx.ASGITransport` | `MockMvc` / `WebTestClient` | Запросы к приложению без сети |
| `StrEnum` | Java `enum` | Значения — строки, удобно хранить в БД |
| `@dataclass(frozen=True)` | Java `record` | Неизменяемый объект-значение |

  api/

    alerts.py          AlertService: правила таблицы 7, антифлуд, SOS

  bot/

Слои зависят друг от друга сверху вниз: `api`/`bot` → `services` → `storage`. Сервисы не знают про HTTP
и Telegram-апдейты, поэтому их легко тестировать напрямую. Единственная точка, где сервис касается
Telegram, — `OutboxDispatcher`.

## 5. Схема базы данных

```
devices 1───* device_guardians *───1 guardians
   │1
   ├──* bind_codes
   ├──* packets 1──0..1 positions
   │       └──────0..1 events 1──* live_locations
   ├──* events
   └──* device_commands 1──* command_waiters
outbox (chat_id, event_id?)       ← очередь исходящих сообщений
```

Время везде хранится как **unix-секунды UTC** (`BIGINT`). Так не возникает путаницы с часовыми
поясами, а значения сравниваются простыми числами. Время для людей форматирует `Texts` с учётом `DISPLAY_TZ`.

### devices — устройства

| Поле | Тип | Зачем |
|---|---|---|
| `id` | TEXT PK | «cane-01», совпадает с `dev` в пакетах |
| `name` | TEXT | «Трость Ивана» для сообщений |
| `token_hash` | TEXT UNIQUE | SHA-256 токена. Сам токен не хранится: утечка базы не даёт права слать пакеты. UNIQUE-индекс позволяет быстро искать устройство по токену |
| `hmac_secret` | TEXT | Секрет HMAC. Хранится открыто, потому что серверу нужно самому вычислить подпись. Хешировать его нельзя |
| `period_s` | INT | Период передачи. Уходит в `cfg.period_s`, от него считается порог «молчит» |
| `enabled` | BOOL | Администратор может отключить устройство |
| `created_at` | BIGINT | Дата регистрации |
| `last_seen_at` | BIGINT | Время приёма последнего пакета (по часам сервера). Основа проверки «молчит» и `/status` |
| `last_packet_type` | TEXT | Тип последнего ненакопленного пакета. Если это `batt_crit`, тревога о молчании пишет «вероятно, выключилась» |
| `state_ts` | BIGINT | Время (`ts`) пакета, из которого взят снимок ниже. Нужен, чтобы старый досланный пакет не затёр свежие данные |
| `bat_v`, `bat_pct`, `net`, `rssi`, `sats`, `hdop`, `fix` | | **Снимок состояния** для `/status`. Не нужно искать последний пакет |
| `silence_alerted_at` | BIGINT NULL | Когда сообщили «не выходит на связь». Не NULL — значит уже сообщили, повторять не надо |

### guardians и device_guardians — сопровождающие и привязка (многие ко многим)

| Поле | Зачем |
|---|---|
| `guardians.chat_id` PK | ID чата Telegram. В личном чате совпадает с ID пользователя |
| `display_name` | «Мария (@maria)» — для «тревогу принял(а) …» и «подключился …» |
| `bind_failures`, `bind_blocked_until` | Защита от подбора кода |
| `device_guardians(device_id, chat_id)` PK | Связь «многие ко многим»: у трости несколько сопровождающих, у сопровождающего может быть несколько тростей. Индекс по `chat_id` нужен middleware доступа |
| `bound_at` | Порядок сопровождающих |

### bind_codes — одноразовые коды

| Поле | Зачем |
|---|---|
| `code_hash` PK | SHA-256 нормализованного кода (верхний регистр, без дефисов). Как и токен, в открытом виде не хранится |
| `device_id` | К какому устройству привязывает |
| `kind` | `passport` (из CLI, бессрочный) или `invite` (из `/invite`, на 24 ч) |
| `created_by_chat_id`, `created_at`, `expires_at` | Кто и когда выпустил, срок действия |
| `used_at`, `used_by_chat_id` | Одноразовость: использованный код второй раз не сработает |

### packets — журнал пакетов и защита от дубликатов

| Поле | Зачем |
|---|---|
| `id` PK | |
| `device_id`, `seq` + **UNIQUE(device_id, seq)** | Защита от дубликатов. Дубликат определяется по паре, а не по «seq меньше максимального», поэтому накопленные пакеты принимаются в любом порядке |
| `type`, `ts`, `buffered`, `payload` (JSON) | Исходный пакет целиком: для отладки и отчёта об испытаниях |
| `effective_ts` | `ts` устройства, если ему можно верить, иначе время приёма |
| `received_at` | Когда пришёл на сервер. Индекс `(device_id, received_at)` |

### positions — точки маршрута

Создаются только из пакетов с `fix=true` и ненулевыми координатами. Поля: `ts` (время фикса),
`lat`, `lon`, `sats`, `hdop`, `net`, `packet_id`. Индекс `(device_id, ts)` ускоряет запросы
«последняя позиция» и «последние 10 точек». Сортировка идёт по **времени фикса**, а не по порядку
прихода. Поэтому накопленные пакеты, пришедшие позже свежих, не становятся «последней позицией».

### events — события и тревоги

| Поле | Зачем |
|---|---|
| `type` | 7 типов от устройства + серверные `silent` и `back_online` |
| `ts`, `created_at` | Когда произошло (по устройству) и когда сервер узнал. Антифлуд считается по `created_at`: он ограничивает частоту сообщений людям |
| `buffered` | Пришло с задержкой (из OfflineBuffer) |
| `lat`, `lon` | Место события (из пакета или последняя известная позиция) |
| `notified`, `suppressed_reason` | Отправлено ли и почему нет: `cooldown`, `stale`, `gps_loss_not_reported` |
| `acked_by_chat_id`, `acked_at` | Кто нажал «✅ Принял» (только SOS) |
| `reminders_sent`, `next_reminder_at` | Напоминания о непринятом SOS |
| `live_until` | До какого момента двигать живую карту SOS |

Индекс `(device_id, type, created_at)` используется в проверках антифлуда.

### device_commands и command_waiters — очередь команд устройству

| Поле | Зачем |
|---|---|
| `name` | Пока только `locate_now` |
| `status` | `pending` → `delivered` (отдана в ответе) → `done` / `expired` |
| `created_at`, `delivered_at`, `completed_at`, `expires_at` | Жизненный цикл и TTL |
| `command_waiters(command_id, chat_id)` | Кто ждёт свежую позицию: ответ получат только они |

### outbox — очередь исходящих сообщений

| Поле | Зачем |
|---|---|
| `chat_id`, `method` (`text`, `location`, `live_location`, `edit_live`), `payload` (JSON) | Что и кому отправить |
| `event_id` | Связь с событием (для живой карты SOS) |
| `status` (`pending`, `sent`, `failed`), `attempts`, `next_attempt_at`, `last_error` | Повторы с экспоненциальной паузой |
| `sent_message_id`, `sent_at` | Результат: ID сообщения в Telegram |

### live_locations — живые карты SOS

`(event_id, chat_id)` → `message_id`, `live_until`. Нужна для `editMessageLiveLocation`: чтобы
сдвинуть точку, нужно знать ID ранее отправленного сообщения в каждом чате.

## 6. Разбор модулей

### 6.1. Конфигурация и время: `config.py`, `clock.py`

`Settings` — класс pydantic-settings. Каждое поле читается из одноимённой переменной окружения
(`bot_token` ← `BOT_TOKEN`) или из `.env`. Ограничения заданы прямо в типах:

```python
port: int = Field(default=8000, ge=1, le=65535)
silence_periods: int = Field(default=3, ge=1)
```

`env_ignore_empty=True` означает, что пустое значение (`DEV_ENDPOINTS=`) считается «не задано»,
а не пустой строкой. Метод `effective_bot_token()` реализует правило: в DRY_RUN токен не нужен,
без DRY_RUN его отсутствие — ошибка конфигурации при старте (fail fast, как ошибка биндинга
`@ConfigurationProperties` в Spring).

`Clock` — протокол (аналог интерфейса) с одним методом `now() -> int`. Сервисы **никогда не вызывают
`time.time()` напрямую**: они получают `now` параметром от того, кто их вызвал. В тестах используется
`FakeClock`, и «прошло 10 минут» — это просто `clock.advance(600)`. Поэтому тесты молчания, антифлуда
и напоминаний выполняются мгновенно. В Java для того же служит `java.time.Clock`.

### 6.2. Хранилище: `storage/database.py`, `models.py`, `repositories.py`

**`Database`** создаёт асинхронный движок SQLAlchemy (`create_async_engine`) с драйвером aiosqlite
и фабрику сессий. При каждом подключении к SQLite выполняются настройки:

```python
cursor.execute("PRAGMA journal_mode=WAL")  # читатели не блокируют писателя
cursor.execute("PRAGMA foreign_keys=ON")  # SQLite по умолчанию не проверяет FK
cursor.execute("PRAGMA busy_timeout=5000")  # подождать до 5 с, если база занята другим процессом
```

Транзакция — это контекстный менеджер:

```python
@asynccontextmanager
async def transaction(self) -> AsyncIterator[AsyncSession]:
    async with self._write_lock, self._sessions() as session, session.begin():
        yield session
```

`session.begin()` фиксирует транзакцию (commit) при нормальном выходе из блока `async with` и откатывает
(rollback) при исключении. Это ровно семантика `@Transactional`. Пример использования:

```python
async with ctx.db.transaction() as session:
    device = await authenticate_device(session, ...)
    ...
```

**Зачем `_write_lock` (`asyncio.Lock`).** SQLite допускает только одного пишущего. Без блокировки две
корутины одного процесса могли бы начать транзакции на чтение, а затем обе попытаться перейти к записи.
SQLite в таком случае сразу отвечает `SQLITE_BUSY`, `busy_timeout` здесь не помогает. Глобальная
асинхронная блокировка выстраивает транзакции процесса в очередь. При нагрузке прототипа (одна трость,
пакет в 30 с) это ничего не стоит. При переходе на PostgreSQL блокировку можно убрать (см. п. 11).
Транзакции короткие: внутри них нет сетевых вызовов к Telegram, это важно.

**`models.py`** — ORM-модели в стиле SQLAlchemy 2.0. Тип `Mapped[int | None]` одновременно задаёт
тип Python и nullable-колонку:

```python
class Packet(Base):
    __tablename__ = "packets"
    __table_args__ = (
        UniqueConstraint("device_id", "seq", name="uq_packets_device_seq"),
        Index("ix_packets_device_received", "device_id", "received_at"),
    )
    id: Mapped[int] = mapped_column(primary_key=True)
    seq: Mapped[int] = mapped_column(BigInteger)
    ts: Mapped[int | None] = mapped_column(BigInteger)
    ...
```

`BigInteger` для `seq` и `chat_id` выбран с расчётом на PostgreSQL: `seq` бывает до 2³²−1,
а chat_id в Telegram длиннее 32 бит. Связи (`relationship`) намеренно не используются. В асинхронном
SQLAlchemy ленивая загрузка связей приводит к ошибкам, поэтому все выборки явные, через репозитории.
Таблицы создаются вызовом `Base.metadata.create_all` при старте (аналог `ddl-auto=update`, только без
изменения существующих таблиц).

**`repositories.py`** — функции-запросы: `latest_position`, `guardian_chat_ids`, `active_command`,
`due_sos_reminders` и т. д. Каждая функция принимает сессию и делает один запрос:

```python
async def latest_position(session: AsyncSession, device_id: str) -> Position | None:
    query = (
        select(Position)
        .where(Position.device_id == device_id)
        .order_by(Position.ts.desc(), Position.id.desc())
        .limit(1)
    )
    return await session.scalar(query)
```

### 6.3. Безопасность: `security.py` и `api/device_auth.py`

```python
def constant_time_equals(left: str, right: str) -> bool:
    return hmac.compare_digest(left.encode("utf-8"), right.encode("utf-8"))


def token_matches(stored_hash: str, presented_token: str) -> bool:
    return constant_time_equals(stored_hash, sha256_hex(presented_token))


def sign_body(secret: str, body: bytes) -> str:
    return hmac.new(secret.encode("utf-8"), body, hashlib.sha256).hexdigest()
```

- **Сравнение в постоянное время.** Обычное `==` прекращает сравнение на первом несовпавшем символе.
  По времени ответа атакующий мог бы подбирать подпись побайтно (timing attack). `compare_digest`
  всегда сравнивает строку целиком. Строки переводятся в байты: `compare_digest` с не-ASCII `str`
  выбросил бы исключение, а так кириллица в заголовке просто не совпадает (это проверяет тест).
- **Токен хранится только в виде SHA-256.** Устройство находится по хешу (индекс UNIQUE),
  после чего хеши ещё раз сравниваются в постоянное время.
- **Ключ HMAC** — строка секрета в UTF-8, как в прошивке (`strlen(CANE_HMAC_SECRET)`).

Порядок проверок в `authenticate_device` намеренно такой: **сначала аутентификация, потом разбор
JSON.** Неаутентифицированный клиент не получает никакой информации о схеме и не заставляет сервер
тратить время на разбор.

```python
token = headers.get(TOKEN_HEADER)
if not token:
    raise ApiError(401, "invalid_token", f"Нет заголовка {TOKEN_HEADER}")
device = await repositories.find_device_by_token_hash(session, sha256_hex(token))
if device is None or not token_matches(device.token_hash, token):
    raise ApiError(401, "invalid_token", "Неизвестный токен устройства")
if hmac_required:
    _verify_signature(device, headers.get(SIGNATURE_HEADER), body)
if not device.enabled:
    raise ApiError(403, "device_disabled", ...)
```

**Защита от повтора (replay).** Подпись покрывает всё тело, включая `seq`. Перехваченный пакет можно
отправить повторно, но такой `seq` уже есть в `packets`, поэтому сервер ответит `dup: true` и ничего
не сделает. Отдельные nonce или временные метки для этого не нужны.

### 6.4. API устройства: `api/schemas.py`, `api/device_routes.py`, `api/errors.py`

`TelemetryPacket` описывает формат раздела 5.6 с диапазонами:

```python
class TelemetryPacket(BaseModel):
    model_config = ConfigDict(extra="ignore")
    dev: str = Field(pattern=r"^[A-Za-z0-9_-]{1,32}$")
    seq: int = Field(ge=0, le=MAX_SEQ)
    ts: int | None = Field(default=None, ge=0)
    type: PacketType
    fix: bool = False
    lat: float | None = Field(default=None, ge=-90, le=90)
    ...

    @model_validator(mode="after")
    def require_coordinates_with_fix(self) -> Self:
        if self.fix and (self.lat is None or self.lon is None):
            raise ValueError("при fix=true поля lat и lon обязательны")
        return self
```

`extra="ignore"` позволяет новым прошивкам добавлять поля, не ломая сервер. Свойство `has_valid_fix`
дополнительно отбрасывает точку (0, 0): так часто выглядит неинициализированный GPS.

Роут `receive_packet` (п. 2) объявлен сразу на двух путях. Декораторы FastAPI можно ставить друг
на друга, поэтому `/event` — полный синоним `/telemetry`:

```python
@router.post("/telemetry", response_model=DeviceReply)
@router.post("/event", response_model=DeviceReply)
async def receive_packet(request: Request) -> DeviceReply:
```

Роут принимает `Request`, а не pydantic-модель параметром. Это сделано намеренно: для HMAC нужны
**сырые байты** тела, а автоматический разбор FastAPI их не сохраняет.

Пакетный `/telemetry/batch` проверяет одну подпись на всё тело. Каждый элемент проверяется отдельно,
поэтому один испорченный пакет не мешает принять остальные. Ответ содержит статус каждого элемента.

`ApiError` и `api_error_handler` — аналог `@ControllerAdvice`. Любая ошибка API приходит в формате
`{"error": код, "detail": подробности}` и пишется в лог как предупреждение
(`Отклонён запрос POST /api/v1/telemetry от 127.0.0.1: 401 invalid_signature`). Это главный
инструмент отладки для разработчика прошивки.

### 6.5. Приём пакета: `services/ingest.py`

```python
async def accept(self, session, device, packet, now) -> bool:
    if await repositories.packet_exists(session, device.id, packet.seq):
        return False
    effective_ts = resolve_effective_ts(packet.ts, now)
    stored = await self._store_packet(session, device, packet, effective_ts, now)
    position = await self._store_position(session, device, packet, stored, effective_ts)
    _update_device_state(device, packet, effective_ts)
    await self._commands.on_packet(session, device, packet, position, now)
    incoming = IncomingPacket(device, packet, stored.id, effective_ts, position)
    await self._alerts.on_packet(session, incoming, now)
    return True
```

- **Дубликаты.** Проверка «уже есть такой seq?» и вставка выполняются внутри одной транзакции под
  `_write_lock`, поэтому между ними никто не вклинится. Ограничение UNIQUE в базе — вторая линия
  защиты. Тест-мутация подтвердил: если убрать проверку, сработает именно UNIQUE.
- **Время.** `resolve_effective_ts` доверяет `ts` устройства, только если оно позже 2024-01-01 и не
  больше чем на 10 минут в будущем. Иначе берётся время приёма. Так обрабатываются случаи «GPS ещё
  не выдал время» (`ts = null/0`) и сбитые часы.
- **Снимок состояния.** `_update_device_state` обновляет `bat_pct`, `net` и другие поля, только если
  пакет не старее уже учтённого (`state_ts`). Досланный пакет двухчасовой давности не покажет в
  `/status` давно разряженную батарею как текущую.
- **Контакт регистрируется и для дубликатов.** Повторный SOS — тоже признак того, что устройство на
  связи. Поэтому `register_contact` вызывается до проверки дубликата (`begin_exchange`).

### 6.6. Тревоги: `services/alerts.py`

Главный метод:

```python
async def on_packet(self, session, incoming, now) -> None:
    await self._update_sos_tracking(session, incoming, now)
    if incoming.packet.type == PacketType.POS:
        return
    place = await self._resolve_place(session, incoming)
    event = await self._record_event(session, incoming, place, now)
    reason = await self._suppression_reason(session, event, now)
    if reason is not None:
        event.suppressed_reason = reason
        return
    event.notified = True
    notification = await self._build_notification(session, incoming, event, place, now)
    await self._notifier.to_guardians(session, incoming.device.id, notification, now)
```

1. **`_update_sos_tracking`.** Если пакет свежий и с фиксом, а у устройства идёт SOS (`live_until > now`),
   для каждой живой карты ставится в outbox команда `editMessageLiveLocation`.
2. **`_resolve_place`** выбирает место события. Если в пакете есть фикс, берутся его координаты.
   Если нет — последняя позиция из базы (её возраст известен, отсюда «7 мин назад»). Если и её нет —
   координаты из пакета, которые прошивка передаёт как «последние известные». Иначе карты не будет.
3. **Событие всегда сохраняется**, даже если уведомление подавлено. Это журнал для отчёта об
   испытаниях.
4. **`_suppression_reason`** — антифлуд:
   - `stale`: событие досланное и старше `BUFFERED_ALERT_MAX_AGE_MIN`, кроме `sos` и `batt_crit`;
   - `gps_loss_not_reported`: `gps_ok` отправляется, только если **последнее отправленное**
     GPS-событие было `gps_lost`. Иначе человек получил бы «восстановлен» без «пропал», или получил бы
     его дважды при «дребезге» сигнала;
   - `cooldown`: уведомление того же типа уже отправлялось недавно (`COOLDOWN_*`). SOS не подавляется
     никогда, кроме дубликата `seq`.
5. **SOS** строится в `_sos_notification`: предыдущие SOS этого устройства перестают напоминать и
   двигать карту, у нового выставляются `next_reminder_at` и `live_until`. Сообщение получает кнопку
   «✅ Принял», карта — `live_period = 600`. Досланный с задержкой SOS приходит без живой карты: двигать
   нечего.

Подтверждение SOS (`acknowledge_sos`) проверяет, что нажал именно привязанный сопровождающий. Затем
выставляет `acked_*`, отключает напоминания и сообщает **остальным**, кто принял тревогу.
`send_due_sos_reminders` вызывается из фонового монитора.

### 6.7. Команды устройству и /where: `services/commands.py`

- `request_location` переиспользует уже активную команду `locate_now` (одна на устройство) и добавляет
  чат в `command_waiters`. Повторный `/where` из того же чата получает ответ «уже отправлен».
- `take_command_for_reply` вызывается при каждом обмене с устройством. Она берёт самую старую
  активную команду, при первой выдаче переводит её в `delivered` и **возвращает её снова в каждом
  ответе**, пока команда не выполнена. Если ответ с командой потерялся в GPRS, следующий обмен
  доставит её повторно.
- `on_packet` закрывает команду. Признак выполнения — первый **ненакопленный** пакет, пришедший
  после выдачи команды (статус `delivered`). Если в нём есть фикс, ожидающим уходит «📍 Свежая
  позиция» с картой, иначе — «спутники не видны». Накопленный пакет команду не закрывает: он старый.
- `expire_overdue` (из монитора) переводит команды старше `LOCATE_TIMEOUT_S` в `expired` и сообщает
  ожидающим, что трость не ответила.

### 6.8. «Устройство молчит»: `services/presence.py`

```python
def _is_newly_silent(self, device: Device, now: int) -> bool:
    if device.silence_alerted_at is not None or device.last_seen_at is None:
        return False
    reference = max(device.last_seen_at, self._started_at)
    return now - reference > self.silence_threshold_s(device)
```

- Порог — `SILENCE_PERIODS × period_s` у **каждого устройства свой** (таблица 7: «нет пакетов дольше
  3 периодов»).
- Однократность обеспечивает поле `silence_alerted_at` **в базе**, а не в памяти. Поэтому после
  перезапуска сервера тревога не повторяется.
- `max(last_seen_at, started_at)`: если сервер сам был выключен два часа, после запуска все устройства
  выглядели бы «молчащими». Отсчёт начинается не раньше старта сервера, и устройства успевают
  выйти на связь.
- Устройства, которые ни разу не выходили на связь, и отключённые устройства пропускаются.
- `register_contact` (из ingest) сбрасывает флаг и, если он был выставлен, отправляет
  «✅ Связь восстановлена (не было N мин)».

### 6.9. Привязка: `services/binding.py`

- `generate_bind_code` использует `secrets.choice` (криптостойкий генератор, как `SecureRandom`) и
  алфавит **без похожих символов** (нет 0/O, 1/I): код переписывают с бумаги. Формат `ABCD-EFGH`,
  32⁸ ≈ 10¹² вариантов.
- `normalize_bind_code` оставляет только буквы и цифры в верхнем регистре: `hzqs 75pe` = `HZQS-75PE`.
- `bind` по шагам: блокировка → поиск кода по хешу → проверка «использован или истёк» → уже
  привязан? → привязка, отметка `used_at`, уведомление уже привязанных сопровождающих. Неверные
  попытки считаются; после `BIND_MAX_FAILURES` подряд наступает блокировка на `BIND_BLOCK_MIN`.
  Даже при 5 попытках в час подбор 10¹² вариантов занял бы миллионы лет.
- Попытка привязаться повторно к своей же трости код **не тратит**.

### 6.10. Исходящие сообщения: `services/notifier.py` и `services/outbox.py`

`Notifier` не отправляет ничего сам: он добавляет строки в `outbox` в **текущей транзакции**.

```python
def to_chat(self, session, chat_id, notification, now) -> None:
    text_payload = {"text": notification.text}
    if notification.sos_ack_event_id is not None:
        text_payload["sos_ack_event_id"] = notification.sos_ack_event_id
    self._enqueue(session, chat_id, OutboxMethod.TEXT, text_payload, notification, now)
    if notification.point is not None:
        self._enqueue_point(session, chat_id, notification, notification.point, now)
```

Если транзакция откатится (например, на ошибке в середине обработки), сообщения тоже не появятся.
Если зафиксируется, сообщения гарантированно будут отправлены, даже если сразу после commit сервер
упадёт. Этим outbox отличается от простого «отправить после commit» в памяти.

`OutboxDispatcher.deliver_due` отправляет их:

```python
async with self._db.transaction() as session:
    messages = await repositories.pending_outbox_messages(session, BATCH_SIZE)
blocked_chats: set[int] = set()
for message in messages:
    if message.chat_id in blocked_chats:
        continue
    if message.next_attempt_at > now or not await self._deliver(message):
        blocked_chats.add(message.chat_id)
        continue
```

- Строки читаются короткой транзакцией, а **запросы к Telegram идут вне транзакции**: медленный
  Telegram не держит блокировку базы и не тормозит приём пакетов.
- **Порядок в чате.** Если сообщение в чат не ушло или ещё ждёт повтора, остальные сообщения этого
  чата в текущем проходе пропускаются (`blocked_chats`). Карта не придёт раньше своего текста. Другие
  чаты при этом не ждут.
- **Ошибки:**
  - `TelegramRetryAfter` (флуд-контроль) — повтор через указанное Telegram время;
  - `Forbidden` (бот заблокирован), `BadRequest`, `NotFound` — бесполезно повторять, статус `failed`;
  - сетевые и прочие ошибки — повтор с паузой 2, 4, 8 … 300 с, до `OUTBOX_MAX_ATTEMPTS` попыток.
- Для живой карты после отправки сохраняется `LiveLocation(event_id, chat_id, message_id)`.
- `wake()` выставляет `asyncio.Event`. `run_forever` ждёт его не дольше `OUTBOX_POLL_S`: новые
  сообщения уходят сразу, а отложенные повторы подбираются по таймеру.

### 6.11. Фоновый монитор: `services/monitor.py`

```python
async def run_once(self) -> MonitorReport:
    now = self._clock.now()
    async with self._db.transaction() as session:
        report = MonitorReport(
            silent_devices=await self._presence.check_silent_devices(session, now),
            sos_reminders=await self._alerts.send_due_sos_reminders(session, now),
            expired_commands=await self._commands.expire_overdue(session, now),
        )
    if report.has_news:
        self._outbox.wake()
    return report
```

`run_forever` вызывает `run_once` каждые `MONITOR_INTERVAL_S` секунд и перехватывает исключения,
чтобы одна ошибка не остановила проверки навсегда. Тесты вызывают `run_once()` напрямую с
`FakeClock`, не дожидаясь таймера.

### 6.12. Тексты: `services/texts.py`

Все формулировки собраны в одном месте: их удобно править и переводить. Ключевые функции:

```python
def format_ago(seconds: int) -> str:
    if seconds < 60:
        return "только что"
    if seconds < 3600:
        return f"{seconds // 60} мин назад"
    ...
```

(В коде вместо чисел 60 и 3600 стоят константы `SECONDS_PER_MINUTE` и `SECONDS_PER_HOUR`.)

`Texts.clock()` показывает `14:31` для сегодняшних событий и `07.10 14:31` для более ранних,
в часовом поясе `DISPLAY_TZ` (`zoneinfo`; на Windows базу поясов даёт пакет `tzdata`). Имена устройств

### 6.13. Бот: `bot/handlers.py`, `bot/access.py`, `bot/keyboards.py`, `bot/setup.py`

Роутеры собираются функцией `build_routers()`, а не на уровне модуля. В aiogram один экземпляр
`Router` можно подключить только к одному `Dispatcher`, а тесты создают много приложений.

```python
guarded = Router(name="guarded")
guarded.message.middleware(BoundGuardianMiddleware())
guarded.callback_query.middleware(BoundGuardianMiddleware())
guarded.message.register(handle_where, Command("where"))
...
```

Три роутера проверяются по порядку:
- `public` — `/start`, `/help`, `/bind` доступны всем;
- `guarded` — всё остальное, только для привязанных;
- `fallback` — ответ «не понимаю» на любой другой текст.

**`BoundGuardianMiddleware`** — белый список chat_id (раздел 5.5: «бот отвечает только chat_id,
привязанным через одноразовый код»). Он загружает трости этого чата. Если их нет, отвечает «вы не
привязаны», и хендлер не вызывается. Если есть, кладёт их в `data["devices"]`. aiogram подставляет
аргументы хендлера по **имени параметра** (похоже на `@RequestParam`), поэтому хендлер получает
готовый список:

```python
async def handle_where(message: Message, ctx: "AppContext", devices: list[Device]) -> None:
    for device in devices:
        await answer_where(message, ctx, device.id)
```

`ctx` попадает в хендлеры через `dispatcher["ctx"] = context` (workflow data — общий словарь
зависимостей диспетчера). Если сопровождающий привязан к нескольким тростям, каждая команда отвечает
по каждой из них.

Ответы на команды (`/where`, `/status`) отправляются **напрямую** (`message.answer`), а не через outbox:
это синхронный ответ на действие человека, и при ошибке он сам повторит команду. Через outbox идут
сообщения, которые инициирует сервер: тревоги и свежая позиция.

Кнопки описаны фабриками `CallbackData` (`sos_ack:5`, `unbind:cane-01`). Это типизированный аналог
разбора строк: `SosAckCallback.filter()` сам разбирает `callback_data` и передаёт хендлеру
`callback_data.event_id`.

`setup.py` содержит меню команд, которое при старте регистрируется через `setMyCommands`. Тогда
в Telegram при вводе `/` появляются подсказки.

### 6.14. Режим DRY_RUN: `bot/dry_run.py` и `bot/simulated_chat.py`

В aiogram каждый вызов Bot API проходит через «сессию» (`BaseSession.make_request`). Обычная сессия
делает HTTP-запрос к `api.telegram.org`. `RecordingSession` подменяет только этот слой:

```python
async def make_request(self, bot, method, timeout=None):
    call = _to_call(method)
    if self.pending_failures:
        error = self.pending_failures.pop(0)
        raise error
    self.calls.append(call)
    logger.info("[TG → %s] %s", call.chat_id, describe_call(call))
    content = json.dumps({"ok": True, "result": self._fake_result(call)})
    response = self.check_response(bot=bot, method=method, status_code=200, content=content)
    return cast(TelegramType, response.result)
```

- Вызов записывается в `calls`: тесты проверяют по нему, что и кому было бы отправлено.
- В лог выводится понятная строка (`sendLocation 59.959315,30.310752 live=600s`).
- Возвращается правдоподобный ответ: объект `Message` с `message_id`, через стандартный
  `check_response` aiogram. Остальной код не знает, что Telegram ненастоящий. Поэтому DRY_RUN проверяет
  **тот же код**, что работает в бою, отличается только последний сетевой слой.
- `pending_failures` позволяет тестам имитировать ошибки Telegram (сеть, флуд-контроль, блокировку).

`SimulatedChat` делает обратное: строит JSON входящего `Update` (как если бы Telegram прислал сообщение)
и подаёт его в `dispatcher.feed_update`. Срабатывают те же фильтры, middleware и хендлеры, что и при
настоящем polling. Это используют тесты и эндпоинт `/dev/bot`, а через него — утилита `devchat`.

### 6.15. Сборка и запуск: `context.py`, `app.py`, `__main__.py`

`build_context` — ручной DI-контейнер. Он создаёт объекты в нужном порядке и передаёт зависимости
через конструкторы:

```python
notifier = Notifier()
outbox = OutboxDispatcher(db, bot, clock, settings)
commands = CommandService(notifier, texts, settings.locate_timeout_s)
alerts = AlertService(settings, notifier, texts)
presence = PresenceService(notifier, texts, settings.silence_periods, started_at=clock.now())
...
context.dispatcher["ctx"] = context
```

В Spring это сделали бы `@Configuration` и `@Bean`. Здесь всё видно явно, и тест может подставить свои
`clock` и `bot_session`. Жизненный цикл описан в п. 8.

### 6.16. CLI и devchat: `cli.py`, `devchat.py`

`cli.py` построен на argparse с подкомандами (как Spring Shell или picocli). Каждая подкоманда — асинхронная
функция, которая получает `Toolkit` (база + `DeviceRegistry`), а `run()` вызывает её через
`asyncio.run`. CLI не создаёт бота, поэтому `BOT_TOKEN` для него не нужен. `add-device` печатает
готовый `secrets.h` и может сохранить конфиг симулятора. `devchat.py` — небольшой HTTP-клиент к
`/dev/bot`.

### 6.17. Симулятор: `simulator/`

Симулятор **не импортирует код сервера**: подпись и формат пакета реализованы в нём заново
(`simulator/device.py`), как это сделает прошивка. Поэтому сквозной прогон проверяет совместимость
двух независимых реализаций контракта, а не код сам с собой.

- `physics.py` — `Walker` (прогулка от ИТМО на Кронверкском со случайным поворотом, дрожание GPS
  ±3 м) и `battery_percent` (таблица «напряжение → %» из раздела 4.3, с линейной интерполяцией).
- `device.py` — `VirtualCane`:
  - собирает пакет и подписывает его;
  - по коду ответа решает, что делать (200 — принято; 4xx — выбросить; 5xx или сеть — в буфер);
  - копит OfflineBuffer (до 200 записей) и досылает его;
  - выполняет `locate_now`;
  - запоминает `seq` в файле (аналог NVS).
- `scenarios.py` — сценарии из таблицы 7 (`walk`, `sos`, `still`, `battery`, `gps_loss`, `offline`,
  `errors`, `serve`, `all`).

## 7. Сценарии по шагам

### 7.1. SOS (рис. 5)

1. Пользователь удерживает кнопку ≥ 2 с. Прошивка отправляет `{"type":"sos", "seq":20, ...}`.
2. Сервер проверяет токен и подпись (`authenticate_device`).
3. `accept`: такого `seq` нет, пакет сохраняется в `packets`, позиция — в `positions`.
4. `AlertService.on_packet` создаёт `events(type=sos)`. Антифлуд SOS не подавляет.
   `_supersede_previous_sos` гасит напоминания старых SOS. Выставляются `next_reminder_at = now + 120`
   и `live_until = now + 600`.
5. `Notifier.to_guardians` добавляет в outbox для **каждого** привязанного сопровождающего текст
   с кнопкой «✅ Принял» и `live_location` (живую карту).
6. Commit. Устройству уходит `200 {"ack":20, ...}`, и прошивка прекращает повторы (рис. 5).
7. `OutboxDispatcher` отправляет `sendMessage` и `sendLocation(live_period=600)`, сохраняет
   `live_locations` с `message_id`.
8. Если ответ потерялся и прошивка повторила пакет с тем же `seq=20`, сервер ответит `dup: true`,
   и второго сообщения не будет (проверено тестом и в e2e: «seq=20 … (дубликат)»).
9. **Режим SOS.** Прошивка шлёт `pos` каждые 15 с. Каждый такой пакет через `_update_sos_tracking`
   ставит `editMessageLiveLocation`, и точка на карте двигается. Через 10 минут правки прекращаются.
10. Если через 2 минуты никто не нажал «Принял», монитор шлёт «Напоминание #1» (до 3 раз).
11. Мария нажимает «✅ Принял». `acknowledge_sos` записывает её, напоминания прекращаются, Пётр
    получает «Тревогу SOS … принял(а) Мария». Если Пётр тоже нажмёт кнопку, увидит «уже принял(а) Мария».
12. **SOS без фикса** (человек в подъезде): берётся последняя известная позиция, в тексте
    «GPS-фикса нет… последняя известная позиция (7 мин назад)», карта статичная.

### 7.2. /where (рис. 6)

1. Сопровождающий отправляет `/where`. aiogram получает update через long polling.
2. Middleware проверяет chat_id, хендлер `handle_where` вызывает `answer_where`.
3. В транзакции `request_location` создаёт или находит `locate_now` (`pending`) и добавляет чат
   в `command_waiters`. Затем читаются устройство и последняя позиция.
4. **Сразу** уходит ответ: «📍 последняя позиция **5 мин назад** (14:28, спутников: 7). Запросил
   свежую — пришлю примерно через 30 с» и `sendLocation`. Если позиций нет — «позиция пока
   неизвестна», без карты.
5. Через ≤ 30 с устройство выходит на плановый обмен. В ответе `take_command_for_reply` отдаёт
   `cmd: "locate_now"`, статус становится `delivered`.
6. Прошивка читает фикс внеочередно и сразу шлёт `pos`.
7. `CommandService.on_packet`: пакет не накопленный, команда `delivered`, значит она выполнена (`done`).
   Ожидающим (и только им) уходит «📍 Свежая позиция» с картой.
8. Если пакет пришёл без фикса — «спутники сейчас не видны». Если за 5 минут ответа нет — монитор
   переводит команду в `expired` и пишет «не ответила».

Итоговая задержка: не больше периода обмена (30 с) плюс время получения фикса, как и сказано в
разделе 5.7.

### 7.3. Неподвижность

1. Прошивка (Alert Manager) видит смещение < 25 м за 10 минут и шлёт `{"type":"still","still_min":10}`.
2. Сервер создаёт событие и проверяет антифлуд: «нет движения» не чаще раза в 10 минут.
3. Уходит «🧍 Трость Ивана: нет движения 10 мин» с картой.
4. Через 30 минут прошивка шлёт напоминание `still_min=40`. Оно проходит: 30 минут больше 10.
5. Если прошивка из-за ошибки шлёт `still` каждую минуту, сопровождающий получит не больше одного
   сообщения за 10 минут. Остальные события сохранятся с `suppressed_reason="cooldown"`.

### 7.4. Досылка накопленных пакетов

1. Связи нет. Прошивка пишет пакеты в OfflineBuffer, в том числе событие `still`.
2. Устройство молчит дольше 3 периодов. Монитор отправляет «⚠️ не выходит на связь» один раз.
3. Связь восстановилась. Первый же пакет вызывает `register_contact`, и уходит «✅ Связь восстановлена
   (не было 15 мин)».
4. Накопленные пакеты приходят с `buffered: true`, со своими `seq` и `ts`, возможно не по порядку
   (в e2e — 28, 30, 31, 32, 29).
   - Каждый `seq` новый, все принимаются.
   - Позиции попадают в `positions` со своим `ts`. «Последняя позиция» определяется по `ts`, поэтому
     старая точка не становится текущей.
   - Снимок состояния не откатывается (проверка `state_ts`).
   - Накопленный `still` моложе 30 минут рассылается с пометкой «⏳ Событие произошло в 12:03,
     получено с задержкой». Старше 30 минут — только сохраняется. SOS и `batt_crit` рассылаются
     всегда.
   - Накопленные пакеты не закрывают `/where` и не двигают живую карту SOS.

### 7.5. «Устройство молчит» и разряд

1. Приходит `batt_crit`. Уходит «🔴 критический разряд», в `devices.last_packet_type` записывается `batt_crit`.
2. Прошивка засыпает. Через `3 × period_s` монитор находит устройство: `silence_alerted_at` пуст,
   порог превышен. В одной транзакции выставляется флаг, создаётся событие `silent`, в outbox
   ставится «⚠️ не выходит на связь… вероятно, трость выключилась» с последней позицией.
3. Следующие проверки устройство пропускают, потому что флаг уже стоит. Тревога однократная, в том
   числе после перезапуска сервера.
4. Трость зарядили и включили. Первый пакет сбрасывает флаг, уходит «✅ Связь восстановлена».

## 8. Асинхронность и запуск в одном процессе

### Как работает asyncio

Python-сервер работает в **одном потоке**. В нём крутится цикл событий (event loop), который по
очереди выполняет корутины (`async def`). На каждом `await` корутина может уступить управление:
например, пока ждёт ответа от SQLite (aiosqlite выполняет запрос в фоновом потоке) или от Telegram.
За это время цикл успевает обработать другой HTTP-запрос или апдейт бота. Это похоже на Spring WebFlux
или Netty: мало потоков, неблокирующий ввод-вывод. Принципиальное отличие от Tomcat с пулом потоков:
**одна блокирующая операция без `await` (например, `time.sleep`) остановила бы весь сервер.** Поэтому
весь ввод-вывод здесь асинхронный: aiosqlite, aiohttp внутри aiogram, `asyncio.sleep`.

Состояние гонки в этой модели возможно только на `await`. Поэтому `asyncio.Lock` в `Database` защищает
транзакцию целиком: между «проверили seq» и «вставили» могут быть `await`, но другая транзакция в
это время не начнётся.

### Как запускаются FastAPI и aiogram вместе

`python -m cane_server` вызывает `uvicorn.run(create_app(settings), ...)`. uvicorn создаёт event loop и
вызывает **lifespan** приложения:

```python
@asynccontextmanager
async def _lifespan(app: FastAPI) -> AsyncIterator[None]:
    ctx: AppContext = app.state.ctx
    await ctx.db.create_schema()
    await _prepare_bot(ctx)
    tasks = [_spawn(coroutine, name) for name, coroutine in _background_jobs(ctx)]
    try:
        yield
    finally:
        await _stop(tasks)
        await ctx.bot.session.close()
        await ctx.db.dispose()
```

1. Создаются таблицы.
2. `_prepare_bot` удаляет webhook и проверяет токен (`getMe`). Неверный токен — понятная ошибка
   и остановка. Telegram временно недоступен — предупреждение, сервер всё равно стартует. Затем
   регистрируется меню команд.
3. `_background_jobs` запускает три задачи `asyncio.create_task`:
   - `outbox` — `OutboxDispatcher.run_forever()`;
   - `monitor` — `BackgroundMonitor.run_forever()`;
   - `telegram-polling` — `dispatcher.start_polling(bot, handle_signals=False, close_bot_session=False)`.
     Её нет в режиме DRY_RUN.
4. `yield`: приложение работает, uvicorn принимает HTTP-запросы. Все задачи делят один event loop.
5. При `Ctrl+C` uvicorn завершает lifespan: задачи отменяются (`task.cancel()` бросает в них
   `CancelledError`), закрываются HTTP-сессия бота и пул соединений с базой.

`handle_signals=False` нужен, потому что сигналы (`Ctrl+C`) обрабатывает uvicorn. Если бы aiogram
поставил свои обработчики, они бы конфликтовали. `close_bot_session=False` нужен, потому что сессию
бота использует и outbox, а закрывается она в lifespan.

**Long polling** (рис. 6: getUpdates) означает, что бот сам ждёт новые апдейты у Telegram. Серверу не
нужен публичный адрес для бота, достаточно исходящего интернета. Публичный адрес нужен только для
приёма пакетов устройства. Альтернатива — webhook (Telegram сам присылает POST), но тогда нужен
HTTPS-адрес и для бота, а на демонстрации в локальной сети это неудобно.

## 10. Принятые решения, альтернативы, отступления от документа

### Решения и альтернативы

| Решение | Почему | Альтернатива |
|---|---|---|
| **Transactional outbox** для уведомлений | Устройство получает `ack` сразу, не ожидая Telegram (важно для GPRS). Сообщения не теряются при сбое Telegram или процесса. Есть повторы | Отправлять прямо в обработчике (как нарисовано на рис. 5): проще, но медленный Telegram задерживает ответ устройству, а при ошибке сообщение теряется. Брокер сообщений (RabbitMQ, Redis): надёжно, но лишний сервис для прототипа |
| **SQLAlchemy ORM** | Переход на PostgreSQL сменой `DATABASE_URL` (раздел 5.5). Знакомая модель «сущность + сессия», как JPA | Чистый aiosqlite и SQL: меньше зависимостей и «магии», но SQL пришлось бы переписывать под PostgreSQL |
| **Один `asyncio.Lock` на транзакции** | Простой и надёжный способ избежать `SQLITE_BUSY` в одном процессе | `BEGIN IMMEDIATE` на каждую транзакцию; на PostgreSQL блокировка не нужна вовсе |
| **Дубликаты по UNIQUE(device_id, seq)** | Работает при любом порядке досылки | «Принимать только seq больше максимального»: ломается на досылке не по порядку и после перезагрузки |
| **HMAC всегда обязателен** | Одна ветка кода в прошивке; токен по GPRS виден, а подпись — нет | Требовать HMAC только для GPRS: сервер не может надёжно отличить канал |
| **Команда повторяется в каждом ответе до выполнения** | Потеря ответа по GPRS не теряет `/where`; повторное выполнение безвредно | Отдать один раз и ждать подтверждения: нужно отдельное поле подтверждения в протоколе |
| **Живая геопозиция при SOS** | Одна обновляемая карта вместо 40 сообщений за 10 минут режима SOS | Отправлять каждую позицию отдельным сообщением (спам) или не пересылать вовсе (теряется смысл режима SOS) |
| **Long polling** | Бот работает без публичного адреса, в том числе на ноутбуке в локальной сети | Webhook: быстрее и экономнее, но нужен HTTPS-адрес |
| **Тексты в одном классе `Texts`** | Удобно править формулировки и проверять их в тестах | Шаблоны (Jinja2) или i18n-файлы, если понадобятся другие языки |
| **Время — int unix-секунды** | Совпадает с форматом устройства, нет путаницы с поясами | `DateTime(timezone=True)`: удобнее в SQL-отчётах |
| **Ручной DI (`build_context`)** | Явно, без «магии», тесты подменяют зависимости через аргументы | Контейнер (`dependency-injector`, `Depends` FastAPI): меньше кода сборки, но больше неявности |

### Где реализация отступает от документа архитектуры

| Документ | Реализация | Причина |
|---|---|---|
| `/api/v1/telemetry` (5.6) и `/api/v1/event` (рис. 4, 5) | Один обработчик, `/event` — синоним | Противоречие в документе; одна схема проще для прошивки |
| Рис. 5: тело `{type, lat, lon, bat, seq}` | Единая схема 5.6 (`bat_v`, `bat_pct`) | Противоречие; поле `bat` не поддерживается |
| Заголовки токена и подписи не названы | `X-Device-Token`, `X-Signature` (hex HMAC-SHA256 тела) | Пробел в документе |
| HMAC «для GPRS без TLS» | HMAC обязателен всегда (отключается `HMAC_REQUIRED=false`) | Сервер не может достоверно узнать канал; одна ветка в прошивке |
| В ответе есть только `ack`, `cmd`, `cfg` | Добавлено поле `dup` | Прошивке полезно знать, что пакет — повтор. Лишнее поле она может игнорировать |
| Нет поля для N в «не двигается N минут» | Добавлено необязательное `still_min` | Иначе текст таблицы 7 не сформировать |
| `ts` всегда из GPS | `ts` может быть `null`/`0`, сервер подставит время приёма | До первого фикса времени нет |
| Поведение `seq` после перезагрузки не описано | Прошивка хранит `seq` в NVS; дубликат — по паре `(device, seq)` | Иначе после перезагрузки пакеты считались бы дубликатами |
| Рис. 5: сервер отправляет в Telegram, затем отвечает 200 | Сначала commit и ответ 200, отправка — фоновой задачей сразу после | Transactional outbox: устройство не ждёт Telegram |
| Таблица 8: только `/start`, `/help`, `/bind`, `/where`, `/status`, `/history` | Добавлены `/invite`, `/unbind` | Одноразовый код из паспорта иначе не позволяет второму сопровождающему привязаться |
| Режим SOS: «позиция каждые 15 с», судьба этих позиций не описана | Живая геопозиция Telegram на 10 минут | См. таблицу решений |
| Подтверждения тревоги сопровождающим нет | Кнопка «✅ Принял», напоминания до 3 раз | Без неё SOS легко пропустить |
| Нет пакетной досылки | Добавлен необязательный `/api/v1/telemetry/batch` | Досылка 200 записей по одной через GPRS идёт медленно; прошивка может его не использовать |
| «Устройство молчит — однократно» | Однократно до следующего контакта, затем «связь восстановлена» | Иначе сопровождающий не узнает, что всё в порядке |

## 11. Что и как дорабатывать дальше

1. **PostgreSQL.** Установить `asyncpg` и указать `DATABASE_URL=postgresql+asyncpg://...`. Убрать
   `_write_lock` из `Database.transaction` или сделать его условным (только для SQLite). Схему вести
   миграциями **Alembic** (аналог Flyway/Liquibase) вместо `create_all`.
2. **Очистка истории.** Задача в мониторе, удаляющая `packets`, `positions` и `outbox` старше N дней.
   Чтобы при этом не открылся повтор старых пакетов, нужно хранить для каждого устройства
   «минимальный принимаемый seq».
3. **Webhook вместо polling** на VPS: `dispatcher.feed_webhook_update` в отдельном роуте FastAPI
   плюс `bot.set_webhook(url, secret_token=...)`.
4. **Несколько процессов или серверов.** Сейчас outbox и монитор рассчитаны на один экземпляр.
   Для масштабирования: PostgreSQL + `SELECT ... FOR UPDATE SKIP LOCKED` в outbox и выбор лидера
   для монитора.
5. **MQTT** (раздел 5.7) для мгновенного `/where`. Команда `locate_now` публикуется в топик
   устройства. Сервисы при этом не меняются: нужен ещё один «вход» рядом с `device_routes`.
6. **Настройки из бота:** период передачи и пороги для владельца (`/settings`). В протоколе для этого
   уже есть `cfg`.
7. **Геозоны:** «вышел из безопасной зоны», рассчитываются на сервере по `positions`.
8. **«Снова в движении»** после тревоги неподвижности: расстояние от точки события `still` больше 25 м.
9. **Прокси для Telegram** (если API заблокирован в сети): `AiohttpSession(proxy=...)` в `build_bot`.
10. **Метрики и мониторинг:** эндпоинт Prometheus (аналог Actuator) с числом пакетов, ошибок
    подписи и длиной очереди outbox.
11. **Отчёт об испытаниях из базы:** все пакеты хранятся в `packets.payload`. Скрипт выгрузки в CSV
    даст данные для отчёта о точности GPS и стабильности связи (раздел 3 и 6 ТЗ).
